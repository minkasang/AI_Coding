# CARLAB｜总任务池入口（状态唯一来源说明）

> 总计划：`../MASTER_PLAN.md`；项目组织与验收：`../docs/command/COMMAND_CENTER.md`。
> **只有各模型专属目录中的 `tasks/*.md` 是正式任务卡与状态唯一来源。** 此文件是导航/规则文档，不复制任务状态或人为填写汇总百分比。

## 任务总池的组织方式

```text
agent-workspace/
├── MASTER_TASKS.md
└── agents/
    ├── gpt-6/              (总指挥)
    ├── qwen4/              (平台家族研究)
    ├── deepseek/           (数据协议)
    ├── grok/               (悬架与物理)
    ├── composer-2-5/       (体验与前端)
    ├── gemini-3-8-flash/   (CAD 和 Blender)
    └── hy4/               (渲染质量)
          ├── PROFILE.md
          └── tasks/
                └── R-XX.md    # 任务进度唯一状态源
```

## 不应产生冲突的设计

1. **主任务池不是额外数据库**：总任务池 = 所有 `agents/*/tasks/*.md` 的集合，由 Node 在请求时解析计算。
2. **每个模型的看板是同一数据的筛选结果**：模型看板 = `owner === 模型ID` 的任务，不需要再单独维护 `board.md` 进度。
3. **阶段进度不是 AI 自行编造**：按任务卡中 `## 执行步骤` 的复选框统计；嵌套步骤只统计叶节点，避免父子重复。
4. **任务状态与步骤比例是两个维度**：`ready` 即使有准备性步骤也不等于模型正在运行；`submitted` 表示等待审查；`approved` 需总控/验证方确认。
5. **文件刷新不是实时监控执行进程**：浏览器每 8 秒读取本机文件变更，无法证明具体 AI 此刻在线；若无人更新，进度不会变化。

## 怎么增加/删除/改名一个模型

在 `agents/` 新建一个独立 slug 目录，包含 `PROFILE.md` 与 `tasks/`；`PROFILE.md` 的 `id` 必须与目录 slug 相同；模型可用别名填入 `aliases`。浏览器自动扫描目录。停用模型应先迁移或归档它未完成的任务；不要直接删除已有成果与历史证据。

## 怎么新增任务

1. 总控制定任务 ID、负责模型、前置条件、详细任务说明和验收。
2. 在负责模型的 `tasks/` 新建 Markdown：以 `---` 元数据开头，至少 `id`、`owner`、`title`、`status`。
3. `## 执行步骤` 必须使用 `- [ ] ...`、`- [x] ...`，子步骤缩进两个空格；如有子步骤，它们才是统计单位。
4. 建议还有 `priority`、`stage`、`summary`（一句话）、`method`（怎么做）、`learning`（一点技术知识）、`brief`（详细任务书）和 `lastNote`（一句话进展）。
5. 模型领取时设置 `status: in_progress`。取得证据后勾选步骤，更新 `lastNote`，完成后标 `submitted`。总控审查通过后改 `approved`，失败标 `needs_work`。

## 哪些暂时还未自动化

- 目前不会自动识别用户打开的外部网页上的模型，也不会自动启动它们。
- 本地 CLI Agent 在进入项目时有机会自动读取 `AGENTS.md`，但具体是否自动读取，取决于所使用的产品/工具。普通聊天窗口需要显式让模型读取项目文件。
- 真正的自动派工、文件冲突锁、外部模型 API/CLI 接入以及进度通知属于后续版本，不作为 V1 已实现能力。

## 人工派发与回报入口（V1.1）

- 进入 `http://localhost:5174/#dispatch`，点击模型任务卡的“复制完整任务提示词”并手动粘贴给对应 AI。
- 模型能访问文件：写好源码/研究/验证后，在个人工作目录创建 `reports/<taskId>.md`，写下交付、测试、限制及下一步，更新 `tasks/<taskId>.md` 的 `status`、`lastNote` 和复选框。
- 模型无法访问文件：直接向用户返回可复制完整报告；用户在看板粘贴该文字，页面把原文保存在同一 `reports/<taskId>.md` 并把任务状态设为 `submitted`。
- 网页内“复制回报给 GPT-6 审核”会连同任务 ID 与原文生成审核提示词。总控必须按需检查实际文件，不以提交回报等同于通过测试。
- 任务状态仍仅存在任务卡 Markdown 中，`reports/` 负责事实材料和回报原文，避免双重状态源。回报历史归档于 `reports/history/`。

## 委托模式更新：总控定目标，模型自主拆解

**这是当前默认机制，优先于早期预先填好的任务步骤。** 总控任务卡说明目标与验收，`ready` / `backlog` 时通常不包含执行复选框；这些任务在看板显示“待自主规划”，不能算 0% 完成。执行模型领取后自行研究现有项目，决定所需的具体工作、数量与先后，必要时在自己 `tasks/` 里创建带 `parentId` 的子任务（例如 `RP-01-S01.md`、`displayCode: 02.02.01`）。子任务仍以本模型目录的 Markdown 为唯一进度源，不额外复制状态到总任务池。

提示词必须认真构造，包含目标/上下文/成果/边界/质量/验收/自主权/回报，具体规则见 `docs/command/PROMPT_AND_DELEGATION_STANDARD.md`。预留的探索方向不是强制执行清单。模型不得凭创建任务卡就填写完成率；看板按已创建的真正步骤与子任务汇总进度。
## V1.3 默认闭环：内部任务管理与直接文件交付

- 主模型必须优先按照 `AGENTS.md` 第 0.1 节和 `docs/command/FILE_HANDOFF_PROTOCOL.md` 工作；旧的“每张子任务复制提示词”不是默认流程。
- 用户只需在有文件权限的 AI Coding 工具启动**主任务**，并非启动每个子任务。主 AI 自己决定细分粒度，能使用真正的子代理工具就内部委派；不能使用时自行顺序执行。无需用户插手它的 S01/S02/S03。
- 主模型及其子代理只维护自身模型 `tasks/*.md` 和各自允许目录，真实结果存 `reports/<taskId>.md`、`docs/planning/reports/`、`docs/planning/evidence/` 等；报告和证据文件以任务 ID 命名，看板自动展示。
- **审核时不需要复制粘贴**：用户再次调用 GPT-6 并报任务号，GPT-6 直接读取任务卡/报告/研究证据/代码/测试，给出通过、返工或阻塞。AI 未被调用时不宣称总控在后台自动巡检。
- 仅对没有本地文件访问权限的模型保留网页手动复制/粘贴入口。

## 审核后续派规则（续派版本）

总控不仅审核 `submitted`，还必须从每个模型的父任务卡判断下一步：当前 `in_progress` 则继续、`needs_work` 则返工、`ready` 则可以领取；已 `approved` 且没有下一项主任务时，应给出新的高质量父任务或明确依赖。新的主任务由总控创建，子任务由模型自主创建。细则见 `docs/command/NEXT_TASK_CONTINUITY.md`；看板直接从任务卡读取“各模型下一步”，不维护手工状态副本。
