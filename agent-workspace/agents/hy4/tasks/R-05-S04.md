# R-05-S04｜渲染后端边界与素材许可治理

## 实际结果（真实完成）

- **WebGL vs WebGPU（EVIDENCE，本地 `node_modules/three@0.170.0` 源码）**：`src/renderers/webgpu/WebGPURenderer.js:21-46` 的构造器支持 `parameters.forceWebGL` 直接选 `WebGLBackend`；否则注册 `getFallback`，在 WebGPU 不可用时打印 `THREE.WebGPURenderer: WebGPU is not available, running under WebGL2 backend.` 并回退到 `WebGLBackend`。即 **r170 的 WebGPURenderer 是"WebGPU 优先 + WebGL2 回退"的双后端**，并强制走 node material / TSL 体系（`StandardNodeLibrary`）。
- **边界判断（ENGINEERING_DERIVATION）**：WebGPU 主要改变 GPU 提交与计算能力（更低的 CPU 提交开销、compute/TSL 后处理），**不会自动改善**倒角高光、金属微表面、反射内容或接触阴影——S02 定位的前四项主因全部属于资产与布光层面。当前瓶颈线索是 57–84 mesh/胎 的对象数与 279 次 draw-call 下界，优先应做几何合并/实例化，而非迁移渲染器。
- **保留现有 WebGL 的理由**：项目无打包器（`index.html` 用 importmap 直引 `node_modules/three`）、`package.json` 锁 `three ^0.170.0`、`AGENTS.md:69` 要求非必要不改可运行演示、`MASTER_PLAN`/`RESEARCH_BASELINE:56` 明确 R-05 在前置验收前不启动渲染引擎重构、A-00 旧车基线回归尚未完成。
- **升级触发条件（建议，待总控裁决）**：① 有真实 GPU 的 A/B 基线；② 出现 WebGL 无法满足的明确需求（compute 粒子、TSL 后处理、大量实例）；③ 目标浏览器 WebGPU 可用率与回退路径经实测；④ 单独分支 + 可回滚提交。缺任一不迁移。
- **Blender 离线渲染成本（ENGINEERING_DERIVATION）**：项目已装 Blender 5.2.2（`AGENTS.md:64`），Cycles/Eevee 适合产出"参考级"材质/布光对照图与贴图烘焙，成本是单帧渲染时间与离线资产管线，不能替代实时 FPS；本轮**未运行 Blender**，不声称已产出离线渲染图。
