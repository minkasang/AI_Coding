# CARLAB｜验收后的下一轮任务衔接规则

> 版本：2026-11-14。任务的唯一状态源仍为 `agent-workspace/agents/*/tasks/*.md`；本规则约束总控工作，不复制任务状态。

## 为什么增加这条规则

此前六项规划研究被审核后，模型专属看板只显示“已验收/待返工”，用户不知道哪些模型可以继续做什么。**审核不能以“已批准”为结束，应该提供接续安排。**

## 总控每次审核后必须继续执行的工作

2026-11-22 项目所有者确认：总控每次接续先扫描**全部工作位**的主任务、最新提交与公共交接，以实际文件判断哪一批要审。对当前提交逐项实查，写回通过、返工或明确的阻塞原因。汇报前再次扫描本轮新提交，处理可核验的项目，并确认所有已批准工作位的接续任务或等待条件。

Codex CAD 对话由总控用实际已连接会话发「继续 CARLAB」，并确认已响应或说明具体启动阻塞。外部模型由总控写任务与审核意见，项目所有者只对当前可领取或需返工的外部模型发「继续 CARLAB」，以及确认产品方向。每轮汇报给出要手动启动的准确名单。

1. **查所有模型队列**：不仅列已验收、待审和返工，还要检查是否有 `in_progress` 或 `ready` 的下一轮父任务；没有就明确说明待决理由。
2. **分三类处置**：
   - 研究/实现已通过、有独立的后续工作：创建或激活一张新的**父任务卡**，提供高质量任务目标、边界、交付和验收标准；
   - 上游问题未解决、仍有正在进行的任务：保持原任务 `in_progress / needs_work`，不重复创建相同任务；
   - 需要设计裁决、权限或其他外部依赖：明确 `blocked / backlog` 与依赖，防止无条件推迟。
3. **各模型只拿主任务**：执行模型按 `AGENTS.md` 自行拆子任务、调用工具实际支持的子代理、在自身项目目录维护回报，用户无需重复转发子任务/成果。
4. **验收和派工是两个不同动作**：审核任务提交物的真实性；派工任务卡的唯一来源是模型自己的 `tasks/*.md`；新任务不能因为计划已写而虚称已启动。
5. **按安全门禁推进**：未经 GPT-6 统一裁定，后续研究可以形成**提案/隔离实验**，但不能直接把冲突的坐标、零件身份或真实车辆参数写成已冻结工程规范。
6. **更新看板**：用户在总览“各模型下一步”就能看到相应父任务、状态及目前卡点；已验收的旧任务进入历史而非占据下一轮位置。
7. **保留恢复点**：关键计划变更应通过本地 Git 形成独立提交，避免多模型同时修改。若存在其他模型正在修改的文件，不应擅自覆盖其工作。

## 当前各模型的下一项任务由真实任务卡决定

当某项研究通过后：
- Qwen4 的平台化变型研究与原整车零件树是不同工作；
- DeepSeek 的 PartSpec/Assembly/Joint 方案是在跨系统接口研究后的深化；
- Grok 的双叉臂悬架机构、硬点与测试方案是在真实性分级后的深化；
- Composer 的“让任务下一轮清晰可见”是原 Viewer 研究后的新工作；
- Gemini 若仍在修复 CAD 配合标准，**先完成返工，不另起与返工重叠的主任务**；
- HY4 若仍在修复独立审计，**先完成返工，再领取新的高画质专项**；
- GPT-6 继续执行 A-00 工程基线及待决接口审查，RP-07 受返工/架构门禁约束。

上述只是衔接说明，**不要把此文当作实时状态表**；实时状态通过当前看板/API 获取。

## 项目所有者的操作

在有文件权限的工具里启动一次新父任务即可；模型自行创建子任务和保存结果。每隔一段时间对 GPT-6 说“检查 CARLAB，审核并安排下一轮”，总控先核实文件，再安排新的工作，而不是只回复验收数字。
