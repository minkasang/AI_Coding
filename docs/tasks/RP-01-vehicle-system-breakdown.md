**研究目标**：回答“怎样确保未来这辆小车足够复杂、细节丰富，却不会漏掉关键机构？”

## 研究要求
1. 把实体整车拆到 System → Subsystem → Assembly → Component/Part，优先详细拆轮端/悬架/制动/传动/动力源，每一类均标 `适用架构`、`可选` 或 `必选`。
2. 必须包括非承载式越野、承载式轿车、纯电三种架构差异；同一件跨系统服务时只记录一个规范产品身份，其它系统通过引用关联。
3. 选**发动机**和**双叉臂轮端**两个示例，至少下钻到可建模零件和固定件（如轴承、密封、螺栓、连杆等），标明尚需取得几何依据的项目。
4. 另列“功能树”作为独立视角，例如“制动”功能从踏板、助力、液压到轮端摩擦与电子控制；不能混同产品树。
5. 逐项对照当前总计划，标记 `COVERED` / `MENTIONED` / `MISSING` / `UNKNOWN`；解释不能把已有名称当作完整实现说明。
6. 优先官方技术手册、公开标准说明、厂商资料；足以支撑重要结论的可定位来源（数量按问题复杂度确定），逐项标明事实、假设和未验证内容。引用只说明资料能实际支持的范围。
7. 对过大/需要量产数据的细节提出演示级简化或暂缓，而非无界列举零件。

## 交付/验收
- 1 份分层树（Markdown，带唯一 SYS/ASSY/PART 规范编号建议）；
- 1 份可解析 JSON 物理产品树示例，至少覆盖轮端总成与发动机的多级关系；不用预填虚构的质量或公差数值；
- 一张系统 → 下游验证类别映射，以及经核对、可复查的关键缺口判断（不为凑数量列项）；
- 提出对现有顶层系统分类的修改建议和典型的不应错误混类的案例。
- 提交回报只需一句话结果、交付路径、验证方式、缺口与建议；不得自行修改总计划。
