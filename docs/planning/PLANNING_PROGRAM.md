# CARLAB｜整车系统蓝图与规划缺口审计（研究工作包）

> 版本：2026-11-14 / DRAFT V0.1；状态：总控已建立研究工作包，专题任务尚待各外部 AI 实际领取。关联 `../../MASTER_PLAN.md`。
> 重要：这是原 P0–P5 路线的深化，不是重新创建一个与总计划竞争的新路线。规划产物必须变成可追溯、可验证的工程资产。

## 1. 研究目标与明确边界

把“要做一辆高细节、运动真实、可拆装、可更换底盘配置、能在 Chrome 中流畅展示的汽车”分解为可以交给多个 AI 独立开发的工程系统树与接口清单。

这项工作的完成标志**不是文档页数**，而是能回答：
1. 整车从系统→总成→部件→零件的层级是否足以支持我们想展示的复杂度？
2. 每个零件在装配、运动、液压、电气、热流、控制信号上与谁交互？
3. 哪些参数/模块能够跨车型复用？变更时哪些接口、装配和验证必须联动？
4. 每个总成需要几何、运动学、动力学、画面各做到什么真实性层级？
5. 哪些内容已具备资料/实验支持，哪些是合理假设，哪些需要新研究？
6. 可否从工程蓝图推导出独立、可验收的下游实现任务，而不让 Flash 自己猜接口？

**不做**：在没有装配硬点与资料来源时生成“完整真实汽车”的大批量资产；宣称仿真可用作量产工程或安全认证；立即换成 UE 或 WebGPU；无证据承诺所有车型共享一个车架。

## 2. 分解规则：不要把四种不同的树混成一张

- **物理产品树 / PBS**：Vehicle → System → Subsystem → Assembly → Part。回答“车里有什么”，管理部件身份、替换关系、数量与版本。
- **功能树**：驱动、转向、制动、冷却、乘员保护、供电、能量转换、状态感知等。回答“车要做什么”；一个功能可能跨越多种物理系统。
- **接口与交互图**：机械力/运动、电能/电信号、液压/流体、热量、控制/诊断和接触约束。回答“系统之间怎样相互影响”。
- **车型/平台变型树**：Architecture → PlatformFamily → VehicleVariant → VariantAssembly。回答“能怎样更换、复用与重新生成”。
- **软件任务 WBS**：研究、CAD 生成、材质制作、渲染、仿真、交互、验证。这是开发任务，不要错误地视为汽车物理结构。

一份机构或零件可以出现在若干功能/接口关系中，但在产品树上必须有规范身份；不能把功能树“悬架行驶舒适”当成真实零件，也不能用网站组件名称代替汽车总成。

## 4. 研究结果的统一结构

每个报告必须包含：
1. **研究对象**：对应系统 ID/功能 ID 与适用车型或平台家族。
2. **系统或关系清单**：每一项有标识、上级、输入/输出、对应接口、可复用部分。
3. **设计证据**：厂商一手资料/标准/技术公开资料/实测代码；来源 URL、发布日期或检索时间、可支持的具体论断。
4. **可检验产物**：系统树 JSON/CSV/Markdown、接口表、示意关系图或有限范围的可执行试验之一，不接受只有抽象分析。
5. **遗漏和冲突**：指出 MASTER_PLAN 已覆盖/未覆盖/误分类的部分，至少提出可以证伪的边界案例。
6. **下一步任务**：谁执行、输入文件、输出文件、验收测试和依赖；下游 Flash 不必自己再设计总架构。

每条重要内容必须标记 `EVIDENCE`（有来源支持）、`ASSUMPTION`（为演示显式假设）、`OPEN`（需要新研究）、`OUT_OF_SCOPE`（经决策暂不做）。不得把估计尺寸当作某量产车型真实参数。

## 5. 三个维度分别验收

- **覆盖度**：每个顶层物理系统明确包含/暂不包含/未知，并指定研究负责人；零件清单“多”不等于覆盖完整。
- **关系完整性**：总成之间至少说明连接点、能量/信号/力流和被修改的影响；没有位置与接口时不得声称可装配。
- **工程可信度**：每项几何/运动/仿真/视觉能力分别注明验证级别、已测与未测，不能简单合并一个“完成百分比”。
